# 配置仓目录规划与同步工具 Decisions

## 术语

A1. 本仓库称「模板仓」，接收配置的仓库称「目标仓」

- Decided by: user

## 目录规划

B1. 顶层按作用域分：`user/` 用户级配置，`projects/` 项目级模板，`shared/` 项目模板间共用文件，`scripts/` 同步工具，`docs/` 决策文档，`.claude/` 本仓库自身开发用配置（不参与同步），`.state/` 工具配置与同步状态，`.backup/` 覆盖前的备份

- Decided by: Claude

B2. 模板内的目录结构与目标处的落盘结构 1:1 镜像，工具只搬运文件、不做路径映射与格式转换

- Decided by: Claude
- 这是支持 AGENTS.md、`agents/` 等非 Claude 体系配置的关键：新增任何体系都无需改工具

B3. 用户级按体系分目录：`user/claude/` → `~/.claude/`，未来的其他体系平级新增

- Decided by: Claude

B4. 每个项目模板是 `projects/<模板名>/`，内含一套完整镜像（`.claude/`、`AGENTS.md` 等）

- Decided by: user

B5. 模板之间平级，不做继承或叠加：一个目标仓只对应一套模板。模板之间的公共内容放 `shared/` 作为唯一来源，模板以文件级符号链接引用，不链接目录

- Decided by: user
- 用户级与项目级内容不会复用，`shared/` 只服务项目模板

## 工具的配置与状态

E1. 配置、状态、备份都存放在模板仓内，不在目标仓落任何文件

- Decided by: user

E2. 配置以目标仓为单位，一条记录包含目标仓路径与基于哪套模板

- Decided by: user
- 定制不在这里声明，它就是快照对两侧的差异；目标仓无需感知同步工具的存在

E3. 覆盖或删除文件前先把原内容备份到 `.backup/`，按同步批次分目录

- Decided by: user
- 不自动清理、不限数量，由用户自行删除
- 备份与快照各存各的，不共用存储、不互相派生

E4. 配置、同步状态、备份都不进 git

- Decided by: user
- 它们是本机数据，换到另一台机器就是一次没有任何定制记录的全新接管

E5. 目标仓登记时分配一个短 ID，作为它在状态与备份里的目录名；仓库路径只是可改的属性，仓库移动后更新路径即可，已有快照不受影响

- Decided by: user
- 用户级视为一个固定 ID 的特殊目标

E6. 快照存全文，不只存哈希：每个目标仓的模板侧与目标侧各存一棵镜像原路径的文件树。`settings.json` 也照存全文，键路径在判定时现场解析

- Decided by: Claude
- 三方合并要以快照为 base 交给 `git merge-file`，没有全文就做不了

E7. 所有写入走临时文件加 rename，工作区、快照、配置一律如此

- Decided by: user（原子写），Claude（覆盖范围）
- 中途崩溃不会留下半截文件，也不会留下与工作区对不上的快照

## 同步模型

C1. 快照按「文件 + 目标仓」存成一对：模板侧快照与目标侧快照，允许二者不同。两份快照的差异就是已知定制

- Decided by: Claude
- 工具不必理解哪几行是定制，只要记住上次确认时两边各自长什么样；同步不再有「必须让两边一致」的隐含目标，震荡的根因消失

C2. 变更判定只看内容与快照的三方关系，mtime 不作判定依据

- Decided by: Claude
- clone、拷贝、checkout 都会重置 mtime；拿它判定会把目标仓侧的任何写入都判成待回流改动，是震荡的直接来源

C3. 一次同步是双向的，没有方向参数：每个文件的去向由三方关系唯一确定

- Decided by: user
- 两侧快照相等时，只有一侧偏离就直接往另一侧送

C4. 两侧都改就合并出带冲突标记的内容再挂起，用户面对的是带标记的文件而不是从零合并；能干净合并的工具自行写入。一侧删除、另一侧修改不合并，直接挂起

- Decided by: user（编辑器方案），Claude（自动处理的边界）

C5. 没有快照可用时（换机器、首次接管）按「没有定制」处理，直接用模板版覆盖目标仓，写入后把两侧内容存为快照对

- Decided by: user
- 这一次同步会把目标仓的全部定制抹成模板版，只能靠目标仓自己的 `git diff` 和 `.backup/` 兜底

C6. 用户级与项目级共用同一套快照模型，只是通常不产生定制、两侧快照相等

- Decided by: user
- 多台机器的 `~/.claude/` 视为同一份，不为用户级引入定制机制：某台机器专属的内容放 `settings.local.json`，或干脆不进白名单

C7. 用户级同步范围走白名单：模板仓 `user/claude/` 里有什么才同步什么，`~/.claude/` 下的运行时数据天然被排除，新配置需要手工放进模板仓才纳入

- Decided by: user

C8. 三方合并的 base 取对侧快照，不是本侧快照：把模板侧的变化并进目标侧时 base 取模板侧快照，把目标侧的变化并进模板侧时 base 取目标侧快照。两侧各合一次，互不干扰

- Decided by: Claude
- 三方合并是把 other 相对 base 的变化应用到 current，base 必须取变化来源那一侧的快照。取本侧快照会把「撤销定制」也算成一处变化，合并结果就把定制抹掉了

C9. 只要两侧快照不等（存在已知定制），哪怕只有一侧偏离快照也要走合并，不能直接覆盖对侧

- Decided by: Claude
- 模板侧更新、目标侧没动时直接下发会把定制抹掉，这正是快照对模型要防的事

C10. 读不到东西只分两种情况：确实不存在，或出了故障。只有前者算缺席、可以判成删除；权限不足一类的故障让本次同步整体失败，不写入任何一侧

- Decided by: Claude
- 把故障当成缺席，等于把「我读不到」传播成「对侧也删掉」；扫描目录同理，少扫一批就等于宣告那些文件不存在

## 定制

震荡场景：目标仓做了一处本仓专属的改动 → 被当成通用改动带回模板仓 → 在模板仓撤销 → 撤销本身成了模板仓的新改动 → 下次同步把目标仓的定制抹掉。

D1. 不靠命名约定（`aky-` / `local-` 前缀）区分归属，不把 `@` 当作导入语义、它只是普通文字；配置文件内部没有分层机制可借，定制只能靠工具显式记录

- Decided by: user

D2. 定制以整文件为单位（`settings.json` 以键路径为单位），不做差异块级的选择。「定制」指目标仓这处改动只对它自己成立，既不回流模板仓、也不该被模板仓覆盖

- Decided by: user

D3. 目标仓对受管文件的修改自动回流模板仓，用户在挂起期间撤掉不想要的那些，撤销即登记为定制

- Decided by: user
- 工具不猜测改动意图，用户的撤销就是答案：撤掉的文件两侧快照不等，那就是定制
- 代价要知情：回流后模板仓工作区就带上了这处内容，漏看一次，下一个目标仓同步时会拿到它
- 撤销的窗口只有挂起那一次。回车之后再去模板仓撤销，那就是一次普通的模板侧改动，下次同步会把撤销后的内容下发、抹掉目标仓那处定制

D4. 目标仓新增的文件不自动纳入模板，需要提升为模板文件时由用户显式指认

- Decided by: user
- 新增文件没有快照，与目标仓自有的大量文件无从区分，全部当候选没有意义

## 文件与格式规则

F1. 删除是一次正常改动：文件相对快照消失即视为删除，会传播到另一侧，而不是被对方复活。`settings.json` 的托管叶子键同此

- Decided by: user
- 目标仓删掉模板给的文件属于定制，登记后不再下发；模板仓删掉的文件，同步时从目标仓一并删除

F2. 模板侧删除的文件即使目标侧有定制也直接删，不挂起。删除后清除快照对，不留墓碑：用户若在目标仓 git 还原该文件，它就退化为目标仓自有文件，工具此后不再看它

- Decided by: user（直接删），Claude（清快照对）
- 不留墓碑是「还原即脱管」成立的前提；留了墓碑，还原会被判成目标侧新增，还可能被再删一次

F3. 不追踪模板仓内的重命名与移动，一律按「删一个、增一个」处理

- Decided by: Claude（用户预授权：过于复杂则不支持）
- 配对之后要迁移快照与定制，还要处理两侧同时重命名的组合，等于再建一层路径语义
- 代价是目标仓在新路径上拿到模板版、旧路径连同定制被删；清单会标出这类条目，用户可先手工 `git mv` 把定制挪过去

F4. 可执行位纳入同步，位变化视同一次内容改动；两侧都改且不一致时各留本侧现值并在清单里标注，工具不挑边

- Decided by: user
- 不记的话丢失可执行位是静默失效——文件内容一字不差，钩子却不再触发

F5. `.claude/settings.local.json` 不参与同步

- Decided by: user

F6. `settings.json` 走键级合并：模板托管它声明过的键，目标仓自行增加的键原样保留

- Decided by: user

F7. `settings.json` 的快照单位从整文件降为键路径：对象逐层展开，数组与标量作为叶子，每条路径的判定与传播规则和整文件的一致（字符串数组与冲突另有处理）

- Decided by: Claude
- 粒度取叶子而非顶层键，否则目标仓想给 `permissions` 添一条就得让整个 `permissions` 脱管
- 叶子冲突不写冲突标记（写进 JSON 就没法解析），改成两侧各留现值、清单里点名冲突的键路径、整份文件挂起
- 代价是键级冲突不像文件级那样有标记可以反复拦截：确认一次就收敛成一处定制，此后不再提醒

F8. 元素全为字符串的数组按集合做三方合并：模板新增的元素并进目标仓、模板删除的从目标仓移除、目标仓自己加的保留。元素不全为字符串的数组退回整体叶子处理

- Decided by: Claude
- 这个特判只为 `permissions` 的 allow/deny/ask 而设；`hooks` 那种对象数组没有可靠的元素身份，不值得为它发明匹配规则

F9. `settings.json` 写回时整体重新序列化，保留原有键序、新键追加到末尾

- Decided by: Claude
- 代价是手工排版会被规整掉；要避免就得做文本级最小编辑，为一个格式问题不划算

F10. 符号链接一律跟随，读和写都作用在它指向的真实文件上，链接本身不是同步单位。模板仓的链接不原样复制到目标仓，目标仓拿到的是跟随后的内容副本

- Decided by: user（模板仓会用符号链接做多份共享），Claude（跟随语义）
- 链接是用户显式声明的「这几份是同一份」，回流时写穿到共享源正是它的意思；代价是一处改动会影响所有引用该源的模板
- 把链接原样复制过去会在目标仓留下指向模板仓的路径，必然失效
- 断链与循环跳过并在清单里报出；断链等同这个路径此刻没有内容，它若有快照就按删除传播到另一侧

F11. 删除只删符号链接本身，不碰它指向的真实文件；写入穿透的范围限于同步范围之内，指向范围外的链接不写，跳过并报出。项目级模板侧的同步范围是本模板目录加 `shared/`，用户级只有 `user/claude/`

- Decided by: user
- 两侧都要写的合并，任一侧超出范围就两侧都不写，不留只落一侧的半成品
- 读写跟随、删除不跟随是有意的不对称：范围内的真实文件自有一条判定管着，不该被链接的删除连带；范围外的更不该被波及，写穿过去也是同步动作溢出到不受管的地方

F12. 目录不是同步单位，只在写文件时按需创建，空目录不同步。非文本文件正常参与同步，但不做三方合并，两侧都改时直接挂起

- Decided by: Claude
- 对非文本内容调用三方合并只会产出无意义的冲突标记，不如直接交给用户

F13. 排除规则用模板仓的 `.gitignore` 判定，不硬编码文件名：路径在模板仓被 git 忽略，两侧都不参与同步。`settings.local.json` 的排除独立于此

- Decided by: user
- 单一权威在模板仓，目标仓不必是可用的 git 仓；目标仓自己生成的产物想被排除，得先在模板仓 `.gitignore` 里也写一条
- 用户级同步（`~/.claude/`）本身不是 git 仓，也不需要为它单独判——它由用户自己管，不特殊处理

## CLI

G1. 命令集：`sync user` 同步用户级，`sync <目标仓>` 同步一个目标仓（短 ID 或路径均可），不带参数进交互；`status` 列出各目标仓有多少待同步、多少定制；`add <目标仓路径> --template <模板名>` 登记目标仓；`adopt <文件路径>` 把目标仓或 `~/.claude/` 下的文件提升为模板文件；`--dry-run` 只看不动。用户级与项目级共用 `sync`

- Decided by: user

G2. 一对逃生舱开关 `--force-template` / `--force-target`：忽略快照与对侧改动，以某一侧为准全量覆盖

- Decided by: user
- 它绕过定制保护，误用一次会抹掉一批定制

G3. 挂起时用 `$EDITOR` 打开文件，CLI 不等编辑器退出，停在原地等一次回车确认

- Decided by: user
- 不绑定编辑器退出，用户才能在挂起期间用任意方式改两侧文件

G4. 先写后看：工具把改动写进两侧，CLI 只打印一份清单；项目级的预览就是两侧的 `git diff`，用户级看 `.backup/` 与现状的 diff。回车确认后，工具读两侧此刻的实际内容存为新的快照对

- Decided by: user
- 不自建 diff 渲染，已有的工作区与备份就是更好的界面
- 回车后只读实际内容，不推断用户在挂起期间做了什么
- 一次同步只挂起一次，不逐文件打断
- 快照留到确认之后再更新，中途中断则快照未动，下次重跑仍能正确判定

G5. 写入是否符合预期由用户在同步后自行检查，工具不增加写前确认环节；撤销靠目标仓的 git 或 `.backup/`

- Decided by: user

G6. 用 Python 实现，不引入任何三方依赖，目标版本跟随 macOS 自带（当前 3.12）

- Decided by: user

G7. 入口是一个带 shebang 的可执行 `scripts/sync.py`，直接运行；不做包装脚本、不安装进 PATH

- Decided by: Claude

G8. git CLI 是硬依赖：三方合并用 `git merge-file`，项目级预览用 `git diff`。平台只保 macOS

- Decided by: Claude
- 自己实现三方合并不划算，git 一定装了

G9. 没有人在场时（stdin 不是终端）等不到确认：有挂起项就不落快照并以非零码退出，下次重跑仍从原判定开始；没有挂起项的下发与回流照常落快照

- Decided by: Claude
- 代价是无人值守跑出来的下发与回流没有撤销窗口，「撤销即登记定制」只对挂起项成立
